## 判定规则

- `[x]`：当前版本已满足，可在运行中的原型里验证。
- `[ ] 部分`：已有界面或状态骨架，但未形成规格要求的完整闭环。
- `[ ]`：当前尚未实现。

> 只有完整满足才打勾。仅有占位页、SnackBar 提示、内存 Mock 或单一成功状态，不计为完整完成。

## 结论摘要

当前版本已经完成“可运行的产品方向原型”，不是 P0 可交付版本。完成度最高的是信息架构、推荐展示、歌曲候选语义、基础设备事实展示和 Pad 编辑骨架。

0.2.0 已新增搜索、歌单展示、配对码流程、四步准备向导、资源检查、现场页和命令状态流。主要缺口收敛为登录、真实音频、文件/链接导入、歌单编辑持久化、真实设备联调、持久化、异常/恢复状态和埋点。

## 15. 最终验收定义对照

- [ ] 没有硬件的舞者可以完成推荐、试听、保存、歌单和手机播放。
  - 当前推荐 UI 可用，但真实试听、持久化曲库、歌单和完整播放器缺失。
- [ ] 组织者可以完成音乐、Pad、设备检查和同步。
  - 当前有 Pad 与设备 Mock 界面，没有准备向导和真实同步。
- [ ] App 断开后，RK 和实体控制器继续工作。
  - 尚无 RK 联调，无法验证。
- [ ] App 重连后显示 RK 当前真实状态。
  - 尚无 WebSocket/快照与重连逻辑。
- [ ] 所有关键对象都有加载、空、失败、离线、冲突和恢复状态。
  - 目前只覆盖少量加载、有内容和空状态。
- [ ] 前端可仅依赖产品文档、设计稿和 Mock 契约理解每个页面目标和行为。
  - 当前实现和文档尚未拆成规格建议中的完整前端交付包。

## 16. 建议的下一阶段顺序

1. **完成 Slice 1 的真实手机音乐闭环**：登录 → 推荐/搜索 → 真实试听 → 本地持久化曲库 → 歌单 → 播放队列。
2. **完成设备连接闭环**：手工地址/配对码 → 能力协商 → 快照 → 超时 → 重连。
3. **把 Pad Mock 闭环升级为可恢复闭环**：本地保存 → 版本冲突确认 → 资源同步 → 设备校验 → 实体测试确认。
4. **实现四步准备向导**，把音乐、Pad、设备检查和同步收束成一次任务。
5. **实现 L01 与命令状态机**，严格以 RK 快照作为事实源。
6. **补齐统一状态、埋点、异常恢复和验收测试**。
